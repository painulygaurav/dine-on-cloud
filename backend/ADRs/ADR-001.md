# ADR-001: Strict TypeScript for the Backend

## Status

- **Accepted**
- **Date:** 2026-11-03
- **Author:** Gaurav Painuly (Staff Software Engineer)
- **Reviewer:** Sam (Principal Software Engineer)
- **Related:** ADR-002 (framework), ADR-003 (architecture style)

## 1. Context

Cloud Kitchen is a food-ordering marketplace in the style of Swiggy. Customers browse many restaurants, add items to a cart (one restaurant per cart), place an order, pay, and track delivery. The backend uses MongoDB, Redis and Kafka, and is deployed to a real environment.

It is a solo, portfolio-grade project with one hard non-functional requirement, **Match Day**: a synchronized flash crowd (for example, an India vs Pakistan match on 15 August, everyone ordering at the same over-break). We plan to break the system on purpose with load tests and then fix what breaks.

That shapes the language decision:

- **Contracts cross many boundaries.** HTTP payloads, Mongo documents, Redis values, Kafka events and payment webhooks all carry data between components. A shape mismatch at any of them is a production bug.
- **Mongo is schema-less.** Old documents can lack a field added later, or hold a different type than the code expects. Driver or ODM types describe what we _intend_ to store, not what _is_ stored, so types alone are not enough and runtime validation is required.
- **Kafka events outlive code.** A consumer may read an event written by an older producer version. Event schemas must be explicit and shared.
- **Refactoring will be frequent.** Load tests will drive module splits and data-model changes. We want the compiler to find every broken call site.
- **Solo developer.** There is no teammate to catch a silent contract drift in review, so tooling has to.

Scope: backend and shared contract packages (event schemas, DTO types). The frontend language is a separate decision.

## 2. Decision

We use **TypeScript 5.x in strict mode** for all backend code from the first commit.

Rules:

1. `tsconfig.json` sets `"strict": true` (this already includes `noImplicitAny`). We also enable `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`.
2. **Compile-time types are not trusted at runtime boundaries.** Every untrusted input is parsed with **Zod** schemas, and TypeScript types are _derived from_ those schemas (`z.infer`), so there is one source of truth. Untrusted inputs are:
   - HTTP request bodies, params and query strings
   - Payment webhooks
   - Kafka messages being consumed
   - Documents read from Mongo where the shape may predate the current code
3. Kafka event schemas live in a shared contracts module and are versioned (see ADR-003).
4. `any` is a lint error (`@typescript-eslint/no-explicit-any`). `@ts-ignore` and `as unknown as X` need a comment explaining why, and are reviewed.
5. CI runs `tsc --noEmit` and ESLint on every pull request and blocks merge on failure.

## 3. Options Considered

| Option                       | Pros                                                                                                                  | Cons                                                                                             |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **Plain JavaScript**         | Fastest to start, no build step                                                                                       | No compile-time checking; every contract is implicit; refactors rely on tests alone              |
| **JavaScript + JSDoc types** | No build step; editor hints; `checkJs` is possible                                                                    | Verbose; easy to under-annotate; weaker generics and inference; tooling is second-class          |
| **Strict TypeScript**        | Compiler-checked contracts; safe refactors; schema-derived types; strong ecosystem support (Nest, Zod, Kafka clients) | Build step; time spent modelling types; a false sense of safety if runtime validation is skipped |

### Why not JavaScript or JSDoc

Both leave contract checking optional. In a system with this many integration points and a refactor-heavy roadmap, optional checking drifts. JSDoc with `checkJs` narrows the gap but is awkward for the generic and schema-derived typing we want.

### Why TypeScript

It turns "did I update every consumer of this payload?" from a manual search into a compile error, which matters most when load-test findings force structural changes.

## 4. Consequences

### Positive

- Contract changes surface as compile errors across the repository.
- Zod-derived types remove duplication between validators and type definitions.
- Better editor tooling speeds up working across the modules defined in ADR-003.

### Negative / Risks

- **Types can lie at runtime.** An unvalidated Mongo read typed as `Order` is a fiction. Mitigation: rule 2 and tests for validation paths.
- **Build step and CI time.** Accepted; `tsc --noEmit` on this codebase size is cheap.
- **Complex types can slow reading.** We keep types simple and prefer schema-derived types over clever generics.

## 5. Compliance & Validation

- CI: `tsc --noEmit` plus ESLint with `@typescript-eslint` recommended rules; both required to pass.
- Lint rules forbid explicit `any`.
- Code review checks that every external boundary uses a Zod schema.
- Contract tests: Kafka event schemas are tested against sample payloads.

## 6. Revisit When

- Build or type-check time becomes a measurable drag on the dev loop.
- A required library has unusable typings and wrapping it costs more than the safety is worth.
