# ADR-002: Backend Framework (NestJS on Fastify)

## 1. Context

Cloud Kitchen is a solo, portfolio-grade, deployed food-ordering marketplace (MongoDB, Redis, Kafka). Its defining requirement is **Match Day**, a synchronized flash crowd that we will deliberately load-test to failure and then harden. The framework choice is judged against that.

Criteria:

1. **First-class TypeScript** and compatibility with Zod-derived types (ADR-001).
2. **Low per-request overhead on hot paths.** Order creation and cart operations are where Match Day hurts.
3. **Structure for a modular monolith** (ADR-003): clear module boundaries and dependency wiring without relying only on discipline.
4. **Control over Kafka behaviour.** Under load we must tune partition keys, consumer groups, batching and offset commits, so the framework must not hide these.
5. **Learning value.** The goal is to understand internals, and to be able to explain every layer in an interview.

## 2. Decision

Use **NestJS with the Fastify adapter** (`@nestjs/platform-fastify`), subject to the benchmark spike in section 6.

Rules:

1. **Modules mirror ADR-003 modules.** Each domain module (`catalog`, `cart`, `orders`, `payments`, `tracking`, ...) is a Nest module exposing a public facade; internals are not exported.
2. **Validation uses Zod**, via a Zod-backed pipe (for example `nestjs-zod`), _not_ `class-validator`. This keeps one validation approach across ADR-001 and this ADR. DTO types are derived from Zod schemas.
3. **Kafka is used directly, not through Nest's microservice transport.** A dedicated infrastructure module wraps a Kafka client so we control partition keys, batching and offset commits. (Confirm the chosen client's maintenance status when selecting it.)
4. **Hot-path escape hatch.** If the benchmark shows Nest overhead above the threshold on create-order, that route (or the process that serves it) is implemented as a plain Fastify handler while the rest stays on Nest.
5. Dependency injection is used for infrastructure clients (Mongo, Redis, Kafka) and cross-module facades.

## 3. Options Considered

| Option                                               | Pros                                                                                                                                                             | Cons                                                                                                                |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **Express**                                          | Largest ecosystem; most familiar                                                                                                                                 | No structure; weaker TypeScript story; slower; unmaintained-feeling defaults                                        |
| **Fastify (bare) + DI library** (for example Awilix) | Lowest overhead; schema-based validation and serialization; plugin encapsulation gives module boundaries; full transparency; fits the "build to understand" goal | We design our own conventions (folder layout, DI wiring, module facades); more decisions up front                   |
| **NestJS on Fastify**                                | Conventions and DI built in; modules map onto ADR-003; guards, pipes and interceptors are ready to use; widely recognized                                        | Decorator and DI overhead per request (to be measured); boilerplate; abstraction can hide behaviour; learning curve |
| **Hono / Koa**                                       | Small and fast                                                                                                                                                   | Smaller ecosystem for our needs; less structure; not evaluated further                                              |

### Honest comparison of the two finalists

Bare Fastify is a legitimate choice, not a strawman: its plugin encapsulation can express module boundaries, and a small DI container is not building "a custom framework". The real trade-off is **convention supplied for free (Nest)** versus **transparency and minimal overhead (bare Fastify)**.

### Why Nest, tentatively

- ADR-003's boundaries (facades, no cross-module internals) map directly onto Nest modules, and Nest gives that structure without us inventing and maintaining conventions alone.
- The Fastify adapter keeps the HTTP layer fast; the benchmark checks whether Nest's own layers erode that.
- Nest is widely recognized, which helps portfolio readability.

### What would change this decision

Bare Fastify wins if the benchmark misses the thresholds, or if during implementation the Nest abstractions repeatedly obstruct work we need to control (especially Kafka and request lifecycle).

## 4. Consequences

### Positive

- Enforced module structure supports the modular monolith.
- Guards, pipes and interceptors cover cross-cutting concerns (auth, validation, logging, rate limiting) consistently.
- Fastify underneath keeps raw HTTP performance available.

### Negative / Risks

- **Per-request overhead** from DI resolution, interceptors and pipes on hot paths. Unmeasured until the spike runs.
- **Boilerplate** (module, controller, service files per feature).
- **Abstraction can hide behaviour**, so Kafka stays outside Nest's transport layer (rule 3).
- **Decorator-heavy code** is harder to follow for people unfamiliar with Nest.
- **Less direct exposure to Fastify internals** than bare Fastify, which slightly conflicts with the learning goal. Accepted, and mitigated by the escape hatch.

## 5. Compliance & Validation

- Use the Nest CLI for module scaffolding to keep naming uniform.
- `dependency-cruiser` (or equivalent lint boundary rules) in CI to block circular dependencies and imports of other modules' internals.
- All controller inputs pass through Zod-backed validation.
- The Kafka wrapper is the only place that imports the Kafka client.
