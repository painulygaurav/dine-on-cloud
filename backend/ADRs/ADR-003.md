# ADR-003: Modular Monolith with Kafka Event Backbone

## Status

- **Accepted**, with open items listed in section 7
- **Date:** 2026-11-03
- **Author:** Gaurav Painuly (Staff Software Engineer)
- **Reviewer:** Sam (Principal Software Engineer)
- **Depends on:** ADR-001 (TypeScript), ADR-002 (NestJS on Fastify, currently Proposed)

## 1. Context

Cloud Kitchen is a solo, portfolio-grade, deployed Swiggy-style marketplace: browse, cart, order, pay, track. Its defining requirement is **Match Day**: a synchronized, geographically concentrated flash crowd (for example, India vs Pakistan on 15 August) that we will deliberately load-test until it fails, then fix.

Facts that drive the architecture decision:

- **Domain boundaries are still forming.** Wrong service boundaries are expensive to undo.
- **One developer.** Every extra deployable (pipeline, monitoring, config) is paid for by one person.
- **We want evidence-driven scaling.** The interview story we want is "load testing showed X was the bottleneck, so we split X", not "we split everything up front".
- **Different parts of the system have different load shapes.** Browse is read-heavy and cacheable; orders are bursty writes; tracking is high-frequency small writes. They will likely need to scale independently.
- **Kafka is a project goal**, so the design must say precisely how modules communicate and where Kafka sits.

## 2. Decision

Build a **modular monolith**: one repository and one artifact, split into strictly isolated domain modules. Use **Kafka for durable cross-module events** via a transactional outbox. Extract a module into its own service **only when load tests show it needs independent scaling**.

### 2.1 Modules (initial)

`catalog` (restaurants, menus), `cart`, `orders`, `payments`, `tracking`, `users/auth`, `notifications`. This list may change as requirements firm up.

### 2.2 Communication model

| Interaction                                                                                          | Mechanism                                                    | Why                                                                                   |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| Needs an answer now (for example `orders` asks `catalog` for price and availability)                 | Direct call through the target module's public facade        | Simple and fast; no network                                                           |
| Durable business fact other modules react to (`OrderPlaced`, `PaymentConfirmed`, `DeliveryAssigned`) | **Domain event published to Kafka via transactional outbox** | Survives crashes; replayable; identical whether consumers are in-process or extracted |
| Best-effort, in-process only (cache invalidation, metrics)                                           | In-process event emitter                                     | Cheap; loss is acceptable                                                             |

**Transactional outbox:** the owning module writes its state change and an outbox record in the **same MongoDB transaction** (requires a replica set). A relay process publishes outbox records to Kafka and marks them sent. Delivery is at-least-once, so **every consumer must be idempotent**. Kafka partition keys are chosen per topic (for example `orderId` for the order lifecycle) to preserve per-entity ordering; hot-key skew is a known risk to test.

**Event contracts** are versioned schemas in a shared contracts module (Zod, per ADR-001).

### 2.3 Data ownership

- One MongoDB database, with collections **namespaced by owning module** (for example `orders_*`, `catalog_*`).
- Only the owning module's repository reads or writes its collections.
- **No cross-module `$lookup` or joins.** Data from another module comes through its facade or from events.
- Redis keys are namespaced per module (for example `catalog:menu:{restaurantId}`).
- Migrations are organised per module.

### 2.4 Process roles

The same artifact can start in different **roles** via configuration (for example `api`, `worker`/consumers, `outbox-relay`). This lets us scale or isolate runtime behaviour per role before any module becomes a separate service.

### 2.5 Likely extraction candidates (hypotheses to test)

`tracking` ingestion, the `orders` pipeline, and `payments` handling. These are guesses until Match Day load tests confirm or contradict them.

## 3. Options Considered

| Option                         | Pros                                                                                                                             | Cons                                                                                                              |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **Traditional monolith**       | Fastest start; simplest deploy                                                                                                   | Boundaries erode; extraction later is painful                                                                     |
| **Modular monolith (chosen)**  | Low operational cost; boundaries enforced by tooling; refactoring is cheap while the domain is fluid; extraction path stays open | Boundaries are logical, not physical; discipline and tooling required; no per-module independent scaling at first |
| **Microservices from day one** | Independent scaling and fault isolation; practises distributed-systems skills early                                              | Large infrastructure and debugging overhead for one developer; wrong boundaries are costly; delays the core build |

### Honest counter-argument

Starting with services would exercise distributed-systems skills sooner. We accept the trade because Kafka, outbox and idempotent consumers already exercise those skills inside the monolith, and extraction later gives a measured, evidence-backed story.

## 4. Consequences

### Positive

- One thing to build, deploy and observe at first, which suits a solo project.
- Outbox plus Kafka means extracting a module does not change how it receives events.
- Role-based process configuration gives some scaling control early.

### Negative / Risks

- **Boundary erosion** if imports or cross-module queries creep in. Mitigated by lint rules and review.
- **No independent scaling initially:** one hot module can starve others for CPU or memory within a process. Mitigated by process roles and, eventually, extraction.
- **Extraction is tractable, not free.** Replacing a facade call with a network call introduces timeouts, retries, partial failure and idempotency concerns.
- **Outbox adds machinery** (relay, cleanup of sent records, duplicate handling).
- **Mongo transactions have a cost** and need a replica set, including locally.

## 5. Compliance & Validation

- Lint or boundary tooling (for example `dependency-cruiser`, `eslint-plugin-boundaries`, or Nx module boundaries) fails the build if a module imports another module's internals.
- Each module exposes only an `index.ts` or `*.facade.ts`.
- CI check or review rule: no cross-module collection access.
- Tests for the outbox: crash between DB commit and publish does not lose events; duplicate delivery does not duplicate effects.
- Match Day load tests are the validation of the whole design and drive any extraction.

## 6. Revisit When

- A module is the proven bottleneck or needs independent deploy cadence.
- Process-role scaling is no longer enough.
- Boundary violations keep recurring despite tooling.
