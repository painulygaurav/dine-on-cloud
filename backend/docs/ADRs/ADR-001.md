# ADR-001: JavaScript (ES Modules) with Runtime Validation for the Backend

## Status

- **Accepted**. **Supersedes** the earlier version of this ADR (Strict TypeScript).
- **Date:** 2026-11-06
- **Author:** Gaurav Painuly (Staff Software Engineer)
- **Reviewer:** Sam (Principal Software Engineer)
- **Related:** ADR-002 (framework), ADR-003 (architecture style)

## 1. Context

Cloud Kitchen is a food-ordering marketplace in the style of Swiggy. Customers browse many restaurants, add items to a cart (one restaurant per cart), place an order, pay, and track delivery. The backend uses MongoDB, Redis and Kafka, and is deployed to a real environment.

It is a solo, portfolio-grade project with one hard non-functional requirement, **Match Day**: a synchronized flash crowd (for example, an India vs Pakistan match on 15 August, everyone ordering at the same over-break). We plan to break the system on purpose with load tests and then fix what breaks.

Two kinds of pressure shape the language decision:

**Technical pressure (unchanged from the earlier version):**

- **Contracts cross many boundaries.** HTTP payloads, Mongo documents, Redis values, Kafka events and payment webhooks all carry data between components. A shape mismatch at any of them is a production bug.
- **Mongo is schema-less.** Old documents can lack a field or hold a different type than the code expects, so runtime validation is required whatever the language.
- **Kafka events outlive code.** Event schemas must be explicit, shared and versioned.
- **Solo developer.** No teammate catches silent contract drift in review.

**Project pressure (the reason for this change):**

- **Learning curve.** Adding TypeScript on top of Node, Express, MongoDB, Redis and Kafka multiplies what must be learned at once.
- **Deadlines.** The time to model types and maintain a build step is not available. Delivery of the working system and the Match Day load tests take priority.

Scope: backend and shared contract modules (event schemas). The frontend language is a separate decision.

## 2. Decision

We use **JavaScript (ES modules, current Node LTS)** for all backend code. TypeScript is not used.

Because there is no compiler checking contracts, **runtime validation carries that responsibility**:

1. `package.json` sets `"type": "module"`. Use `import`/`export` everywhere, not CommonJS.
2. Every untrusted input is parsed with **Zod** schemas. Untrusted inputs are:
   - HTTP request bodies, params and query strings
   - Payment webhooks
   - Kafka messages being consumed
   - Documents read from Mongo where the shape may predate the current code
   - Environment configuration, parsed at startup
3. Kafka event schemas live in a shared contracts module and are versioned (see ADR-003).
4. Each module's public facade documents its inputs and outputs with **JSDoc** (`@param`, `@returns`, `@typedef`). Editors use it for hints. No `checkJs` enforcement is required.
5. ESLint runs on every pull request with `no-unused-vars`, `no-undef` and `eqeqeq`, and blocks merge on failure.
6. Tests cover validation paths and the facades between modules, since the compiler will not catch broken call sites.

## 3. Options Considered

| Option                       | Pros                                                                              | Cons                                                                                     |
| ---------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **Plain JavaScript + Zod**   | No build step; fastest to start; lowest learning curve; fits the deadline         | No compile-time checking; refactors rely on tests, lint and Zod; contracts partly implicit |
| **JavaScript + JSDoc types** | Editor hints; `checkJs` can be turned on later                                    | Verbose; easy to under-annotate; weaker inference                                         |
| **Strict TypeScript**        | Compiler-checked contracts; safe refactors; schema-derived types (`z.infer`)      | Build step; type-modelling time; extra learning curve (rejected for now, see below)       |

### Why JavaScript

The earlier version of this ADR preferred TypeScript for refactor safety. That benefit is real, but the learning curve and the deadline outweigh it for this project. Zod, JSDoc, lint and tests cover the most dangerous gaps (runtime boundaries), and the project can still deliver the Match Day story.

### Honest counter-argument

Load-test findings will force structural changes, and without a compiler "did I update every consumer of this payload?" becomes a search plus tests. This is a known cost, accepted knowingly.

## 4. Consequences

### Positive

- No build step; faster feedback loop; less to learn and configure.
- Zod schemas still give one source of truth for runtime shapes, and they carry over unchanged if TypeScript is adopted later.

### Negative / Risks

- **Contract drift is caught late**, at runtime or in tests, not at compile time. Mitigation: Zod at every boundary, facade tests, JSDoc.
- **Refactors are riskier.** Mitigation: keep modules small, keep facades narrow, and keep integration tests for the order flow.
- **Typos and wrong property names** are invisible until executed. Mitigation: ESLint, and good test coverage on services and repositories.

## 5. Compliance & Validation

- CI: ESLint required to pass; tests required to pass.
- Code review checks that every external boundary uses a Zod schema.
- Contract tests: Kafka event schemas are tested against sample payloads.

## 6. Revisit When

- Contract or shape bugs recur despite Zod, lint and tests.
- Refactors become too slow or too risky without compiler help.
- The learning curve or deadline pressure eases enough to adopt TypeScript (the migration path is: add `tsconfig`, rename files to `.ts`, derive types with `z.infer`).
