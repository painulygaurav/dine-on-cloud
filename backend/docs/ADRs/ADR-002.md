# ADR-002: Backend Framework (Express on JavaScript)

## Status

- **Accepted**. **Supersedes** the earlier proposal (NestJS on Fastify), which was never accepted.
- **Date:** 2026-11-06
- **Author:** Gaurav Painuly (Staff Software Engineer)
- **Reviewer:** Sam (Principal Software Engineer)
- **Depends on:** ADR-001 (JavaScript)
- **Related:** ADR-003 (modular monolith)

## 1. Context

Cloud Kitchen is a solo, portfolio-grade, deployed food-ordering marketplace (MongoDB, Redis, Kafka). Its defining requirement is **Match Day**, a synchronized flash crowd that we will deliberately load-test to failure and then harden.

The earlier proposal was NestJS on Fastify with strict TypeScript, pending a benchmark spike. Because of the learning curve and deadlines (ADR-001), we are choosing a smaller, plainer stack:

1. **Speed to a working vertical slice.** Get browse, cart and order working end to end before investing in framework and build-tooling decisions.
2. **Learning value.** Plain Express with hand-built conventions exposes every layer (routing, middleware, error handling, wiring), which suits the goal of explaining each layer in an interview.
3. **Fewer moving parts.** No build step, no decorators, no DI container to learn while the domain is still forming.
4. **Structure still matters.** ADR-003 requires strict module boundaries, so the structure must come from our own conventions and tooling, not from the framework.
5. **Control over Kafka behaviour** (partition keys, batching, offset commits) is unchanged. The framework must not hide it.

## 2. Decision

Use **Node.js with Express (5.x) and plain JavaScript (ES modules)**, per ADR-001.

Rules:

1. **Modules mirror ADR-003 modules.** Each domain module lives in its own folder and exposes one public entry point (`index.js`, its facade). Other modules import only that file, never internals.
2. **Layering inside a module:** routes, controller (HTTP only), service (business logic), repository (the only code touching that module's collections).
3. **Runtime validation uses Zod** at every untrusted boundary (HTTP, config, Mongo reads, Kafka events, webhooks). Without a compiler, runtime validation is the main safety net, so this is not optional.
4. **Kafka is used directly** through a thin infrastructure wrapper, which is the only place that imports the Kafka client.
5. **Centralised error handling and config.** One error-handling middleware, typed application errors, and environment config parsed and validated at startup so it fails fast.
6. **Dependencies are wired by plain module imports and factory functions** for infrastructure clients (Mongo, Redis, Kafka). No DI container for now.
7. **Boundaries are enforced by tooling**, not discipline alone (see section 5).

## 3. Options Considered

| Option                    | Pros                                                                                            | Cons                                                                                                              |
| ------------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **Express + JavaScript**  | Fastest start; largest ecosystem; no build step; everything is visible; easy to explain         | No built-in structure; no compile-time checks; slower than Fastify; conventions are ours to maintain             |
| **Express + TypeScript**  | Same framework with compiler-checked contracts                                                  | Adds build step and type modelling; rejected for now because of learning curve and deadlines (ADR-001)            |
| **Fastify (bare)**        | Lower overhead; schema-based validation; plugin encapsulation                                   | Less familiar; more decisions up front                                                                            |
| **NestJS on Fastify**     | Conventions and DI built in; modules map onto ADR-003                                           | Decorator and DI overhead (unmeasured); boilerplate; heavier to learn before the domain is understood             |

### Honest counter-argument

The earlier ADRs chose TypeScript and Nest to get structure and type safety from day one. Dropping both trades safety for speed. We accept this because of the learning curve and deadlines, the domain is still forming, and the project is solo. If TypeScript is ever wanted, the cost (rename to `.ts`, add `tsconfig`, derive types from Zod schemas) is moderate and well understood.

### What would change this decision

Revisit if any of the following happen (see section 6): boundary violations recur, runtime type bugs reach integration tests or production, or Express request overhead shows up as a Match Day bottleneck.

## 4. Consequences

### Positive

- A working end-to-end slice sooner, with less up-front tooling.
- Full visibility into request handling, middleware and error flow.
- Zod schemas written now carry over directly if we later adopt TypeScript (`z.infer`).
- Express is well known, which helps portfolio readability.

### Negative / Risks

- **No compile-time contract checking.** Shape mismatches across HTTP, Mongo, Redis and Kafka surface at runtime. Mitigation: Zod at all boundaries, plus tests, plus JSDoc on facades.
- **Structure depends on conventions and lint rules.** Boundary erosion is the main risk (ADR-003 §4). Mitigation: section 5.
- **Express performance ceiling** is lower than Fastify. Unmeasured; load tests will tell.
- **Later migration cost** if we move to TypeScript or another framework. Kept low by thin controllers, framework-free services and repositories, and Zod-defined contracts.

## 5. Compliance & Validation

- `dependency-cruiser` (or `eslint-plugin-boundaries`) in CI fails the build if a module imports another module's internals or creates a circular dependency.
- Every module exposes only `index.js`; code review checks that every external boundary has a Zod schema.
- Services and repositories must not import `express`, so they stay portable if the framework changes.
- A basic integration test (health check, 404 and error shape) runs in CI.
- Match Day load tests (k6 or autocannon) are the real validation and may trigger a revisit.

## 6. Revisit When

- Runtime type or shape bugs recur despite Zod validation (revisit ADR-001).
- Boundary violations keep recurring despite tooling.
- Load tests show Express overhead as a top bottleneck (benchmark bare Fastify against Express on `POST /orders` before switching).
- The module count or team grows enough that built-in structure (Nest) would pay for itself.
